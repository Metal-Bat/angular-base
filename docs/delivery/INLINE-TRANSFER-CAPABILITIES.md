# Inline private transfer: current scope and producer handoff

Master V31 belongs to APP-FE-017.UX05, APP-FE-028.UX03 and APP-FE-036.UX01. This continuation reuses BinaryTransfer, CaseFiles/CaseResources, AttachmentAssociation, the existing case coordinator and the profile mutation coordinator. It introduces no uploader service, generic action engine, public storage URL or normal reference-copy workflow.

## Supported implementation

Attachment collections offer a native local chooser and single-file drop, explicit File/Image intent, required captions and exact producer content-type hints. The existing image service normalizes input pixels to WebP before association. Image hint validation therefore checks the stored image/webp type, accepts local image choices, and leaves transformed byte-size validation to the authoritative association service. Original source bytes are not falsely treated as stored image size; upload DTOs expose only a handle. Runtime controls and authoring settings explain the saved-image format and size semantics without rewriting persisted policies. Measured progress, including zero, remains measured; missing totals remain indeterminate. Cancellation owns the byte subscription. Attachment kind is explicitly mapped from the existing SubmissionAttachmentDTO: file/image are retained; unknown kinds never authorize an image preview. The producer already supplies kind/content_type/size_bytes; its historical description as a missing metadata capability was incorrect.

Image previews use the existing authorized business-request/work-item attachment-content GET operations. A known supported image kind, raster content type and positive size at most 10 MiB are required; returned bytes are checked too. Object URLs are local to the mounted preview, revoked on owner/actor/access loss and destruction, and never persisted. Optional preview failure retains Download. Published/submitted sources remain immutable.

A narrow Forms resource seam exposes the existing stable local case owner and authorized content read. Canonical scopes and exact stable row keys retain ownership; rotating opaque current refs are never decoded or treated as stable identities. Same-owner refresh retains confirmed attachments and draft captions. Old reads cannot overwrite a later owner/revision. An active authorization denial clears private content; a transient failure retains confirmed state. Busy commands disable input without removing the current image or local selection. Explicit kind survives an unchanged policy, current-reference refresh and language changes.

The shared native file picker is the existing native-file-control exception, extended for guarded file drops, multiple-file rejection, safe local filename/size display and actor cleanup. It is reused for collection additions/replacements and avatars. Standard business controls use PrimeNG. The existing avatar PATCH singleton semantics, independent name drafts and known-handle read-before-retry remain unchanged.

Upload bytes and association are separate stages. A known uploaded handle stays with the original case/field/row/replacement payload. An unusable acknowledgement requires an authoritative read before retry; an already-applied link is confirmed without another upload or mutation. Discard is local; cancellation does not claim deletion of stored bytes. No cleanup/garbage-collection API is added.

## Precise open producer capabilities

1. **Scalar media association and authorization.** Designer media has scalar string schema. Current forms/application/attachments.py `_collections` accepts only attachment_collection; synchronization writes a list. The existing private upload and attachment-content routes do not authorize a scalar binding. Preserve scalar values/schema, show the unavailable inline capability explicitly, and obtain an approved owning scalar binding/read contract. No collection coercion, generic case-data patch, private storage field exposure or copied upload reference is used as a substitute.
2. **Wildcard MIME semantics.** RenderOptions accepts a persisted wildcard string, while actual `_validate_item` checks exact content-type membership. The frontend now follows actual exact membership; it does not expand or rewrite saved policies. A producer decision/repair is needed before wildcard settings can promise wildcard upload acceptance.
3. **Literal zero count.** RenderOptions permits max_items=0, but actual attachment validation uses `max_items or 256`. Frontend retains the explicit zero count restriction and saved value; backend must reconcile this discrepancy. Byte limits are different: current RenderOptions requires max_item_bytes/max_total_bytes >=1, so byte zero is not a newly accepted contract.
4. **Confirmed original filename projection.** original_filename is private upload storage metadata and absent from SubmissionAttachmentDTO. The frontend shows the safe local selected name while available and the confirmed caption/type/size. Download retains the authorized Content-Disposition filename. It does not fabricate a public filename lookup or expose private entities.

These are frontend handoffs against the recorded producer source and frozen manifest, not approval to alter backend routes, entities, migrations, published pins or shared data. Backend D07's two exact SDK warnings remain VERIFIED_WITH_EXCEPTION; they do not excuse a frontend warning or required skipped test.
